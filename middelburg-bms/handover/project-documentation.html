1Project overview

Purpose

The warehouse stores pharmaceutical products, so temperature and humidity must be kept stable and recorded. The project delivered a web-based Building Management System (BMS) dashboard. Site staff use it to monitor every HVAC unit and room sensor, act on alarms, start and stop the rooftop units, adjust their temperature setpoints, and export recorded data.

Scope

Included

  • Live monitoring of 16 HVAC units: 5 rooftop and 11 hybrid.
  • 6 room sensors (temperature, humidity, CO₂) and 6 fire damper statuses.
  • Start/stop and setpoint control of the 5 rooftop units.
  • Alarm display, including dirty-filter alarms.
  • History logging every 5 minutes, with CSV export.
  • Site host PC, on-site and remote access.
  • User guide, signage, staff training and handover.

Not included / by others

  • HVAC equipment, field wiring and electrical work.
  • JACE station configuration and point mapping (controls integrator).
  • Control of hybrid units (monitoring only, by agreement).
  • Phone/WhatsApp/SMS alarm notifications (not built).
  • Schedules and Auto/Manual selection (no points supplied).
  • Architectural floor plan. The 3D model layout is illustrative.

Key facts

ControllerTridium JACE, Niagara 4, accessed through its OSS REST API (HTTPS)
Points configured295 (289 unit and sensor points + 6 fire dampers)
Writable points10: rooftop start/stop and setpoint (units 1–5). Everything else is read-only.
Write priority1 (highest)
UsersViewer, Operator and Admin roles; operators send commands
Runs onSite host PC, 24/7, as a Node.js service with no database and no internet dependency

2System architecture

Components

ComponentDescription
Field equipmentRooftop units on the BACnet network (station folder Drivers/BcpBacnetNetwork/OFFICES/points/RUT_n). Hybrid units 1–5 on ModbusAsyncNetwork, 6–11 on ModbusTcpNetwork. Room sensors via Modbus TCP gateways (TempEast, TempWest). Fire dampers on FIRE_DAMPERS.
JACE controllerTridium JACE running the Niagara 4 station, configured by the controls integrator. It exposes points through the OSS REST API at https://192.168.1.140/ossRestApiServer (OAuth client credentials, self-signed certificate).
Gatewayscripts/jace-gateway.mjs: obtains and caches the token, serialises all JACE requests, times out unresponsive reads after 4 s, and only writes points on its allowlist.
DashboardPlain HTML/CSS/JavaScript served by scripts/serve.mjs. Libraries are stored locally, so it works without internet.
History loggerscripts/history.mjs: reads every point every 5 minutes and appends to CSV files on the host PC.
Remote accessTailscale private network to the host PC. No ports are opened to the internet.

4Control philosophy

The rules below were agreed on site with the controls integrator on 8 November 2026.

FunctionRule
Rooftop start / stopCommanded from the dashboard (Uni{n}StartCmd, true = start). Confirmed by reading the command back. The card shows whether the supply fan follows.
Rooftop setpointCommanded from the dashboard (Unit{n}Setpoint), range 15–35 °C in 0.5 °C steps.
Rooftop heating / coolingAutomatic changeover in the unit, not commanded. It cools when the space is above the setpoint and heats when the space is below (setpoint − 1 °C). Between the two it does neither, which prevents hunting. Unit{n}Mode true = heating, displayed only. Writing it would lock the mode.
Hybrid unitsMonitoring only. BMS state, mode, fan, setpoint and alarms are displayed. The JACE refuses writes to hybrid mode points, and the gateway allowlist blocks all hybrid writes.
Fire dampersRead-only, shown as OPEN / CLOSED (true = OPEN assumed, to be confirmed by the integrator).
AlarmsEach unit card shows each alarm point as green OK or red ALARM. The dirty filter shows "Clean" or "DIRTY – replace filter". The Alarms page lists all active alarms. Limit-based conditions use illustrative thresholds until approved limits are supplied.

Command priority

Niagara points have a 16-level priority array. The value in force is the highest-priority (lowest number) non-empty slot, not the last write. The dashboard writes at priority 1, so its commands cannot be overridden by schedules or logic at lower priorities. This also means:

  • A value written at priority 1 stays in force until it is released (Workbench: Actions → Auto, or "relinquish"). Leftover priority-1 values from early tests on Unit{n}Mode must be released, or the automatic changeover stays locked (see section 11).
  • Every command is verified by reading the point back from the controller at 1.5, 5 and 15 seconds. The operator sees Sending…, then Confirmed, or a clear failure message.

Safety measures in the software

  • Write allowlist on the host PC: only the 10 rooftop start/stop and setpoint points can be written, whatever a browser sends.
  • A confirmation dialog for every command (old value → new value, optional reason), recorded in the Audit Trail.
  • Viewers cannot send commands. Controls are disabled while the JACE connection is lost.
  • Only live values are displayed. Values that are stale, offline or not mapped show "—" with a label, never an old number presented as current.

7Issues found and how they were resolved

#IssueCause and resolution
1Gateway could not log in although the check tool could.The gateway used an outdated token path from .env. All API paths now come from one shared module (oss-auth.mjs), and outdated keys are ignored and removed.
2Writes returned HTTP 400 with no message.The API client had no write rights. The integrator granted rights, after which writes succeeded.
3Some unit folders and point names did not exist on the JACE (hybrids 1–5, damper paths).Diagnostic scripts probed each expected path. The damper path was corrected twice on site (FIRE_DAMPERS, then HYBRID_n_FIREDAMPER). The hybrid 1–5 folders remain open with the integrator.
4Rooftop units did not change between heating and cooling automatically.Priority-1 values left from early mode tests were overriding the automatic changeover. Mode was made read-only in the dashboard; the integrator must release the leftover values (open item).
5Commands at priority 8 were "Not confirmed".Leftover priority-1 values out-ranked them. Write priority was set back to 1.
6Dashboard showed "overridden" for its own commands.The JACE reports status overridden for any priority write. The warning now appears only when a higher priority than ours is active.
7Dead Modbus networks slowed every poll and command.Reads now time out after 4 s, and a unit folder that does not answer is skipped for 30 s.
8Mistaken change: setpoint made read-only.Only heating/cooling was meant to be read-only. The change was reverted the same day, so the setpoint stays adjustable.
9Handover day: "address already in use :8080" and an old version showing.The scheduled task kept an old copy running as SYSTEM after the folders were replaced. Stopped from an Administrator prompt (taskkill /IM node.exe /F, schtasks /end), then restarted from the new folder. See section 8.

Lessons applied from the ARC Glasshouse project

  • Credentials stay on the server, never in browser code.
  • One token and one JACE request at a time: the JACE's login invalidates older tokens, and parallel reads overload it.
  • Every write is verified by reading it back, because a write can succeed (HTTP 200) yet be overridden by a higher priority.

8Host PC: installation, operation and updates

LocationServer cabinet on site (signed "restricted")
Operating systemWindows, with Node.js installed
Project folderC:\Users\Admin\OneDrive\Desktop\middelburg-bms (at handover; moving it to C:\middelburg-bms is recommended)
Addresshttp://192.168.1.90:8080 on site
Credentials.env in the project folder holds the JACE address and API client ID/secret. It exists only on this PC: it is not in GitHub and not on USB copies. Never print or e-mail it.
Auto startScheduled task "Middelburg BMS" runs scripts\start-bms.cmd at start-up, which restarts the server 10 s after any stop.

Start / restart (Administrator Command Prompt)

taskkill /IM node.exe /F
schtasks /end /tn "Middelburg BMS"
cd C:\Users\Admin\OneDrive\Desktop\middelburg-bms
npm.cmd run dev

Then press Ctrl + F5 in the browser. Use npm.cmd, because PowerShell blocks npm scripts on this PC. Run either the scheduled task or npm.cmd run dev, never both (port 8080 clash).

Recreate the scheduled task (if the folder moves)

schtasks /create /tn "Middelburg BMS" /tr "C:\middelburg-bms\scripts\start-bms.cmd" /sc onstart /ru SYSTEM /f

Install an update

  1. Copy the new middelburg-bms folder to a USB drive. Leave out data, node_modules and .env.
  2. Check the copy is the new version, for example: findstr /c:"Fire dampers" E:\middelburg-bms\js\pages\controls.js
  3. Stop the server (commands above).
  4. Copy over the existing folder, keeping data and credentials:
    robocopy E:\middelburg-bms C:\…\middelburg-bms /E /XD data node_modules /XF .env
  5. Start the server and press Ctrl + F5 in the browser.
OneDrive: keeping the project on a OneDrive Desktop can lock history files during sync, and the SYSTEM account used by the scheduled task may not be able to read it. Move the folder to C:\middelburg-bms and recreate the task.

9Remote access, data and backups

Remote access (Tailscale)

The site has no public IP address, so remote access uses Tailscale, an encrypted private network between the host PC and approved devices. No firewall ports are opened to the internet.

  1. The administrator invites the user to the Tailscale network by e-mail.
  2. The user accepts, installs Tailscale on their device and signs in with the same account.
  3. With Tailscale connected, the user opens http://100.103.134.56:8080. Test with ping 100.103.134.56.

Remove devices of people who leave from the Tailscale admin console. Step-by-step instructions for staff: handover/remote-access-guide.pdf.

Recorded data (history)

WhatEvery point of every unit and sensor, every 5 minutes, while the server is running
Wheredata\history\daily\YYYY-MM-DD.csv (one file per day) and data\history\points\<unit>\<reading>\YYYY-MM.csv
SizeAbout 4–5 MB per day
ExportDashboard → Trends → Stored logs: choose the date range and unit, then Download logs (CSV). Opens in Excel.
GapsNo data is recorded while the host PC or server is off. Failed reads are written as "down" rows, so gaps are visible.

Backups

data\historyThe only copy of the recorded readingsMonthly at least (copy to USB or network share)
.envNeeded to reconnect to the JACE after a PC rebuildOnce, then after any credential change. Store offline and securely.
Source codeAlready in GitHubNo action needed
Restore after a PC failure: install Node.js, copy the project folder, restore .env and data\history, recreate the scheduled task, and run npm.cmd run check to confirm the JACE connection.
